# 简历生成质量诊断

> 2026-09-09 · 依据:生产库真实数据(账号 `569440662@qq.com`)与两份实际产出的对照
>
> 触发:同一批原料,系统生成的简历明显弱于人工用 Claude 写的版本。本文回答「问题出在提示词还是产品设计」。

---

## 0. 结论

**主要是产品设计问题(约 80%),提示词只占约 15%,另有约 5% 是一个渲染 bug。而且提示词那 15% 背后仍然是设计问题**——提示词忠实实现了规格,是规格把「不要编」当成了工作的全部。

一句话概括:

> **Proofly 现在是一个「真实性守门员」,不是一个「简历生成器」。**
> 它能保证简历上没有一个字是假的,但它没有任何机制保证简历上出现了你已经证明过的东西。
> 这是两件事,需要两套规则,目前只有一套。

---

## 1. 证据:原料 vs 产出

生产库里实际存着的东西:

| 项目 | 库里有 | 简历上用了 |
|---|---|---|
| 项目经历 | 10 条(8 条 `measured`、1 条 `estimated`、1 条 `absent`) | 10 条 ✅ |
| **指标 `metrics`** | **60 条**,「AI 成长陪伴助手」一条就有 17 条 | **0 条** |
| `actions` | 「AI 成长陪伴助手」7 条,条条带细节 | **2 条**,且被砍短 |
| `situation` / `task` | 每条经历都填了(最长 126 字) | 0 |
| 技能 `skills` | 82 条(53 strong / 13 weak / 16 none) | 66 条平铺成一段 |
| 任职履历 `employments` | 5 段 | 存在,但未用于分组 |

被丢弃的实测指标举例(全部标着 `measured`,全部躺在 `metrics` 表里):

```
累计服务用户数        5,595 名
累计对话轮数          24,584 轮
AI 模块月触达 UV      1.75 万 UV
AI 模块占全站 MAU     14.5%
情绪倾诉类对话占比    58.2%
情绪倾诉类用户覆盖率  67%
陪伴时段使用占比      40%
意图路由置信度均值    0.905
意图路由置信度中位数  0.95
正常响应率            99.1%
（…此条经历共 17 项,全库共 60 项）
```

### 最关键的一点

**这份简历是干净通过门禁的。**

- 生成时间 `2026-09-09 06:10:10`
- 锁定时间 `2026-09-09 06:12:16`
- `check_results` 中 blocking 记录:**0 条**

也就是说——**一份什么都没说的简历,在现有质量体系里是满分。**

---

## 2. 七个原因(按影响排序)

### ① 十条经历全是默认「简写」→ 每条硬截 2 行

**类型:产品设计 · 影响:最大**

`atom_target_strategy` 表中,该用户两个求职方向**一行记录都没有**。

| 位置 | 内容 |
|---|---|
| `src/lib/targets/strategy.ts:17` | `DEFAULT_RENDER_WEIGHT = "brief"` |
| `src/app/app/resume/baseline-actions.ts:46` | `BULLET_CAP = { expand: 5, brief: 2, one_line: 0, omit: 0 }` |

模型写多少条都会被代码截到 2 条。「每段整整齐齐两行」不是模型的风格,是截断器的结果。

**两层设计错误:**

1. **默认值方向错了。** 简历生成器的开箱默认不应是「所有经历都用最压缩形态」。默认应当是展开,压缩是用户为第五重要的项目主动选择的。
2. **这件事没有被告知。** 工作台选材预览里有个「简写」小标签(`BaselineWorkbench.tsx:446`),但没有任何一处说明「这个方向下 10 条经历全部是默认值,所以每条只会有 2 行」。用户不知道有个开关没打开。

---

### ② 整套质量体系只管「有没有编」,不管「有没有说」

**类型:产品设计 · 影响:最根本**

现有规则清单:

- 门禁六道:G1 措辞与证明度不符 / G2 触发 never_say / G3 编造数字 / G4 事实冲突 / G5 无证据技能 / G6 互斥冲突
- 体检十五码:C1–C15

**没有任何一条问:「这条经历标着 `measured`、挂着 17 个实测指标,你一个都没用,为什么?」**

激励因此是完全单向的:

| 模型的选择 | 后果 |
|---|---|
| 写数字 | 可能撞上 G3 → 整次生成被拦下(死锁修复前还会永久锁死生成) |
| 不写数字 | **零风险,零代价,满分通过** |

模型的行为完全理性。提示词中 `measured` 档写的是「**可以**写精确数字」(`resume-prompts.ts`)——是「可以」,不是「必须」。在 2 行预算 + 猜错有惩罚的条件下,它必然选择「做了什么」而放弃「变成了什么」。

> **「禁止生成」这个产品主张,实现时只实现了「禁止」,没实现「必须用上已有的证据」。**

---

### ③ `actions` 与 `metrics` 在提示词里是两个断开的数组

**类型:数据模型**

模型收到的结构(`baseline-actions.ts` 的 `selectedAtomsJson`):

```json
{
  "actions": ["设计五层优先级个性化打招呼智能体…", "…共 7 条"],
  "metrics": [
    {"name": "冷启动预置问题贡献对话量占比", "to": "15.6%"},
    "…共 17 条"
  ]
}
```

**没有任何字段说明哪个指标属于哪个动作。**

要写出「设计五层优先级问候机制,冷启动预置问题贡献 15.6% 对话量」,模型必须自己猜配对;猜错就是 G3 事故。在预算紧张且猜错有惩罚的情况下,最优解就是全部丢掉。

人工写那份时,配对是人做的。`metrics` 表目前只有 `atom_id`,没有指向具体 action 的引用——**对象模型缺了一层**。

---

### ④ 有了 `employments` 表,渲染层没跟上

**类型:产品设计**

S6 引入任职履历,但 `src/lib/resume/markdown.ts` 只按 `section` 分组,**一条 atom 一个 `###`**:

```
### 润泽园教育集团 · AI成长陪伴助手模块　润泽园教育集团 · 产品专家　2022.02 – 至今
### 润泽园教育集团 · APP战略升级　润泽园教育集团 · 产品专家　2022.02 – 至今
### 润泽园教育集团 · 业务中台数字化　润泽园教育集团 · 产品专家　2022.02 – 至今
```

同一段任职被印成三份工作。ATS 会当成三段互不相干的经历解析,人读起来是排版坏了。

人工版本的结构是「一个雇主标题 + 项目一 / 项目二 / 项目三」。**这个层级数据库里已经有了,只是没有用于渲染。**

---

### ⑤ 公司名被打印两遍(S8 引入的回归)

**类型:bug**

- `title` 由模型生成。模型看得见 `org`,所以写成「润泽园教育集团 · AI成长陪伴助手模块」
- `meta` 在 S8 之后强制取自 `employments`(`profile-sections.ts` 的 `employmentMeta`),格式为「org · title　起止」

两边都带公司名。最严重的一条:

```
### 信华信技术股份有限公司 · Java研发工程师　信华信技术股份有限公司 · Java研发工程师　2015.06 – 2016.06
```

原封不动重复一遍。

S8 之前 `meta` 也由模型生成,它自己会保持一致;S8 把 `meta` 接管了,却没有同步告诉提示词「公司名由代码补,你不要写进 title」。**提示词与渲染层的契约脱节。**

---

### ⑥ 技能栏是 66 个词的倾倒

**类型:产品设计 · 三处叠加**

| 环节 | 问题 |
|---|---|
| 抽取 | `skills.category` 列**82 行全是 `null`**——列建了,从来没填过 |
| 选材 | `select.ts` 的 `selectSkills` 只滤掉 `strength === "none"`,strong + weak 全留,**不设上限** |
| 提示词 | 明写「按给定顺序输出,**不要增删**」——模型被禁止精简 |
| 渲染 | `markdown.ts` 用「、」拼成一整段 |

结果里同时躺着:

> 产品设计 / 产品定义 / 产品规划 / 产品架构设计 / 产品系统设计 / 产品战略规划 / 产品方案与文档设计

七个近义词。**一份什么都会的技能栏等于没有技能栏。** 人工版本是 6 行分类,每行一个能力域。

---

### ⑦ headline 完全不过门禁,且贴着字数下限

**类型:设计漏洞**

`gate.ts:384` 的 `checkAll(blocks, atoms, facts, skills, groups)` 只遍历 `blocks`。**headline 不在 `blocks` 里,一个字都没有被检查过。**

> 全篇唯一没有来源经历的那段文字,也是全篇唯一不受任何约束的文字。

目前它写得保守所以没出事,但它随时可以编造。

同时它只有 79 字,而提示词要求「个人定位段:80–140 字」——踩在下限之下,通篇形容词、零事实:

```
10年互联网产品经验,聚焦C端AI教育与学习产品,擅长从用户需求、产品定义、
AI系统设计到商业化和交付落地,将大模型能力转化为用户真正会使用的学习与成长功能。
```

对照人工版本的定位段开口即是「12 万 MAU / 5,595 名用户 / 21.4% → 32.2%」。

---

### 附:S 和 T 被完全丢弃

`situation` / `task` 每条经历都填了(「AI 成长陪伴助手」那条 78 字),也确实随提示词发给了模型,但在 2 行预算下必然被挤掉。

人工版本最有力的句子恰恰来自 S/T:

> 「针对旧版工具型定位导致的**课程空窗期活跃断崖**,主导 App 从学习工具向成长平台的战略定位重构」

**产品收集了完整的 STAR,只渲染了 A。**

---

## 3. 归因汇总

| 类别 | 占比 | 对应条目 |
|---|---|---|
| 产品设计 / 数据模型 / 渲染 | **~80%** | ① ② ③ ④ ⑥ + S/T 丢失 |
| 提示词 | ~15% | `measured` 档「可以」应为「必须优先」;`brief` 档没给长度下限;headline 无结构要求 |
| 纯 bug | ~5% | ⑤ title / meta 重复 |

## 4. 优化清单

### A. 立刻见效、改动最小(建议先做)

| # | 改动 | 涉及文件 | 风险 |
|---|---|---|---|
| A1 | 默认权重 `brief` → `expand`;并在工作台明确提示「N 条经历全是默认值,去配策略」 | `strategy.ts:17`、`BaselineWorkbench.tsx` | 低。会让所有未配置方向的简历变长,需重新生成才生效 |
| A2 | **新增门禁 G7**:`measured` 经历的块内未出现任何来自该经历 `metrics` 的数值 → **warning**(先不设 blocking) | `gate.ts`、`gate-help.ts` | 低。首次让「有证据不用」成为一件被记录的事 |
| A3 | 修 title / meta 重复:提示词明说「title 不要带公司名」,或渲染时去重 | `resume-prompts.ts` 或 `profile-sections.ts` | 低 |
| A4 | 提示词:`measured` 档「可以写精确数字」→「**必须优先**使用该经历的 metrics」;为 `brief` 档补长度下限 | `resume-prompts.ts` | 低 |
| A5 | headline 纳入门禁检查范围 | `gate.ts` 的 `checkAll` | 低 |

### B. 需要先拍板(结构性)

| # | 改动 | 待决问题 |
|---|---|---|
| B1 | **按 `employment` 分组渲染**——一个雇主一个标题,项目作为其下的子块 | 会改变简历整体结构,影响导出、打印页、`resume_blocks` 的排序模型。是否值得在 Phase 1 做? |
| B2 | **`metrics` 关联到具体 `action`** | 加一列 `action_index` 还是建关联表?已有的 60 条怎么回填——人工、AI 补齐,还是只对新数据生效? |
| B3 | **技能栏分类 + 上限** | `category` 让 AI 补还是人工归一次?上限定多少(建议 24–30)?超出的进「本版取舍」还是直接不显示? |
| B4 | **S/T 进入渲染** | 是作为块的 `summary`(一句话背景),还是只在 `expand` 权重下出现? |

### C. 更远的方向性问题

- **质量体系需要第二套规则。** 现有的 G1–G6 / C1–C15 全是「真实性」规则。是否要引入一组「强度」规则(证据利用率、量化覆盖率、STAR 完整度),并在简历页给出一个可见的分数?
- **门禁的单向激励需要对冲。** 只要「写数字有风险、不写数字无代价」这个格局不变,任何提示词优化都会被模型的风险规避行为消解掉。A2 是最小的对冲,但可能不够。

## 5. 复现方式

本文所有数据经由 Supabase Management API 直接查询生产库得出。关键查询:

```sql
-- 原料盘点
select u.email,
       (select count(*) from atoms a       where a.user_id = u.id) atoms,
       (select count(*) from metrics m     where m.user_id = u.id) metrics,
       (select count(*) from skills s      where s.user_id = u.id) skills,
       (select count(*) from employments e where e.user_id = u.id) emps
from auth.users u;

-- 策略配置(结果为空 = 全部走默认值)
select * from atom_target_strategy where target_id = '<target>';

-- 产出对照
select order_index, title, meta, bullets, template_used
from resume_blocks where baseline_id = '<baseline>' order by order_index;

-- 是否真的通过了门禁
select code, level, title from check_results
where user_id = '<user>' and level = 'blocking' and resolved_at is null;
```
